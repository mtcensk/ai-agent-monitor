# План доработок AI-агента мониторинга

Анализ реализуемости пяти пунктов дорожной карты применительно к текущему агенту
(`agent.py`, ~880 строк, Python stdlib, 4 daemon-потока + Telegram long-poll).

**Стенд:** VDS 4 vCPU / 7,3 ГБ RAM (занято ~1,2 ГБ) / 148 ГБ диска (занято 6 %).
Запаса ресурсов достаточно для всех пунктов, включая стек трейсинга.

Оценки трудозатрат — для одного разработчика с AI-ассистентом, включая развёртывание
и проверку на стенде.

---

## 1. L3-автономия: auto-remediation по плейбукам

**Реализуемость: полная. Трудозатраты: ~2 дня.**

### Что уже есть
- `ACTIONS` + `run_action()` — выполнение команд с аудитом в журнал инцидентов.
- Поток L2: `pending_action` → `/confirm`. L3 — это тот же `run_action`, но с
  триггером от правила вместо человека.
- `baseline_check()` и пороги уже дают детерминированные сигналы для триггеров.

### План доработки
1. Новая секция `playbooks` в agent.py:
   - структура `PLAYBOOKS`: имя → {условие (lambda по снимку метрик/инциденту),
     действие из расширенного `ACTIONS`, cooldown, max_выполнений_в_сутки,
     режим dry-run};
   - `evaluate_playbooks(m, incidents)` — вызов из `metrics_loop` после
     `baseline_check`;
   - расширить `ACTIONS`: `clear_report_queue`, `vacuum_pg`, `restart при росте RSS`
     (утечка памяти: RSS > X и рост N снимков подряд).
2. Безопасность:
   - каждый плейбук стартует в режиме **dry-run** (только сообщение «выполнил бы …»)
     и переводится в enforce после N корректных срабатываний;
   - kill-switch: переменная окружения `AUTONOMY=off|dryrun|enforce`, команда
     `/autonomy` для переключения из Telegram;
   - обязательный cooldown (например, 1 ч) и дневной лимит на плейбук.
3. Аудит: записи вида `action-auto` в журнал инцидентов с причиной срабатывания
   (значения метрик) — пригодится для post-mortem (пункт 5).
4. Проверка: смоделировать рост RSS (стресс-тест), убедиться в dry-run сообщении,
   затем включить enforce и повторить.

### Риски
- Неверно настроенное условие → лишние перезапуски. Митигация: dry-run по умолчанию,
  cooldown, дневной лимит.

## 2. Мультиагентность: observer / diagnostician / executor

**Реализуемость: частичная, в облегчённом виде. Трудозатраты: 2–3 дня (лёгкий вариант), 5+ дней (полная). Приоритет низкий.**

### Оценка
Классическая мультиагентность (независимые процессы, LLM-оркестратор, протокол
сообщений) для стенда из двух сервисов избыточна: текущие 4 потока уже разделены
по ролям, а отказоустойчивость обеспечивают systemd и heartbeat. Реальную ценность
даёт не «несколько агентов», а **явное разделение ответственности в коде**.

### План (лёгкий вариант)
1. Разбить `agent.py` на пакет `ai_monitor/`:
   - `observer.py` — collect_metrics, tail, health (только сбор, без решений);
   - `diagnostician.py` — baseline_check, корреляция, LLM-разбор, RAG;
   - `executor.py` — ACTIONS, плейбуки, run_action;
   - `reporter.py` — отчёты, дашборды, Telegram-отправка;
   - `bus.py` — обмен между ролями через типизированные задачи в state.json
     (или SQLite — есть в stdlib).
2. Протокол: observer пишет «находки», diagnostician превращает их в «диагнозы»,
   executor получает только подписанные диагнозом действия.
3. Проверка регресса: все существующие сценарии (алерты, команды, дайджест)
   работают без изменений поведения.

### Что сознательно не делаем
- LLM-оркестратор между ролями: +30–50 % к расходу токенов, непредсказуемые
  задержки в критическом пути алертинга, выигрыша на двух сервисах нет.

## 3. OpenTelemetry-трейсинг приложений

**Реализуемость: полная, но зависит от доступа к коду приложений. Трудозатраты: 3–4 дня.**

### Что уже есть
- Prometheus + экспортёры собирают метрики; приложение man_reporting уже отдаёт
  `/metrics`. Трейсинг — единственный недостающий столп наблюдаемости.

### План доработки
1. Инфраструктура (~1 день):
   - развернуть OTel Collector и Grafana Tempo (Docker, ~1,5 ГБ RAM — запас есть);
   - подключить Tempo как data source в Grafana, включить traces-to-metrics/logs.
2. Инструментация (~1–2 дня, нужен редеплой приложений):
   - в оба .NET-приложения добавить OpenTelemetry SDK: автoинструментация ASP.NET
     Core, HttpClient, Npgsql (SQL-запросы со временем выполнения);
   - экспорт по OTLP в Collector на localhost;
   - прокинуть `trace_id` в логи приложений (связка трейс ↔ лог ↔ алерт).
3. Интеграция в агента (~1 день):
   - при инциденте запрашивать у Tempo API 3–5 медленных/ошибочных трейсов за
     последние 15 минут и вкладывать в LLM-промпт — анализ станет причинным
     («медленный SQL в отчёте X» вместо «что-то с БД»);
   - команда `/trace` — последние ошибочные трейсы по запросу.

### Риски
- Требуется изменение и редеплой прикладного кода — единственный пункт с такой
  зависимостью. Если код приложений сейчас менять нельзя, пункт переносится.

## 4. SLO вместо порогов: SLI, error budget, burn rate

**Реализуемость: полная. Трудозатраты: ~2 дня.**

### Что уже есть
- `metrics_history` (600 снимков) и журнал инцидентов с длительностями простоев —
  этого достаточно для расчёта availability. MTTD/MTTR уже считаются.

### План доработки
1. Определить SLI:
   - **доступность** = доля успешных health-проб (уже пишутся в историю);
   - **латентность** = p95 времени ответа health/формы (добавить замер в
     `check_health` — сейчас фиксируется только факт успеха).
2. `slo_report()` в agent.py:
   - error budget для цели 99,5 % за 30 дней (≈ 3,6 ч простоя/мес);
   - burn rate: fast (окно 1 ч) и slow (окно 6 ч) — алерт при превышении,
     вместо/рядом с жёсткими порогами;
   - блок SLO в ежедневном дайджесте: остаток бюджета, текущий burn rate.
3. Команда `/slo` — текущие SLI и бюджет по запросу.
4. Проверка: искусственный простой → burn rate растёт, бюджет уменьшается,
   алерт срабатывает раньше порога «недоступно N минут».

### Риски
- Минимальные; чисто вычислительная доработка на существующих данных.

## 5. Автогенерация post-mortem из журнала инцидентов

**Реализуемость: полная. Трудозатраты: ~1–1,5 дня.**

### Что уже есть
- Журнал инцидентов с типами (down/up/error/action) и временными метками,
  `metrics_summary()` за 24 ч, RAG-функции, `build_html_report()`.

### План доработки
1. `build_postmortem(incident_id)`:
   - выбирает пару down→up (или кластер ошибок), подтягивает метрики за окно
     инцидента ±30 мин, связанные действия из аудита;
   - LLM по шаблону: хронология → влияние → первопричина → что сработало →
     action items;
   - результат — HTML-документ (переиспользовать `build_html_report`) в
     `/app/ai_monitor/postmortems/` + файлом в Telegram.
2. Триггеры: автоматически при простое > 5 минут; по команде `/postmortem [N]`.
3. Связка с пунктом 1: в хронологию попадают авто-действия плейбуков.
4. Проверка: сгенерировать post-mortem по реальному прошлому инциденту из журнала.

### Риски
- Качество зависит от LLM; митигация — жёсткий шаблон и факты из журнала,
  модель только связывает и формулирует.

## Рекомендуемая последовательность

1. **Спринт 1 (3–3,5 дня):** плейбуки в dry-run + post-mortem. Сразу дают
   видимый эффект: агент начинает не только сообщать, но и действовать и
   документировать.
2. **Спринт 2 (2 дня):** SLO и burn rate — переводит алертинг с порогов на
   бюджет ошибок, доработка чисто вычислительная.
3. **Спринт 3 (3–4 дня):** OpenTelemetry, когда будет окно для редеплоя
   приложений.
4. **Опционально:** лёгкая мультиагентность как рефакторинг, если кодовая база
   агента продолжит расти.
