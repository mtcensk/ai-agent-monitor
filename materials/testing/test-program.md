# Программа тестирования

**Объекты:** `CntsAdminCon.Refactored` (веб-админка, Blazor Server, .NET 8) и `man_reporting_service_v2` (фоновый генератор отчётов, .NET 8, Quartz cron, HTTP API).

**Версия документа:** 1.0, 16.11.2026

---

## 1. Объекты и объём тестирования

### 1.1. man_reporting_service_v2

Фоновая служба, которая:

- читает настройки отчётов из таблицы PostgreSQL `man_reporting_settings` (опрос каждые `ConfigPollIntervalSeconds`, инкрементально по `report_last_update`);
- ставит каждый включённый отчёт на одноразовый таймер по Quartz-cron;
- выполняет прогон: SQL (PostgreSQL / Oracle / MS SQL) → DataSet → xlsx (ClosedXML) → письмо через SMTP (MailKit, клиентский сертификат);
- хранит секреты зашифрованными AES-256-GCM (`enc:v1:<keyId>:...`), CLI: `genkey`, `encrypt`, `encrypt-db [--apply]`;
- поднимает HTTP API (порт 5080): `GET /reports`, `GET /reports/{id}`, `GET /reports/{id}/status`, `POST /reports/{id}/run`, `POST /reports`, `PATCH /reports/{id}`, `/metrics`, `/health`; защита заголовком `X-Api-Key`;
- не допускает параллельного выполнения одного отчёта (`RunRegistry`); изменения конфигурации во время прогона применяются отложенно.

### 1.2. CntsAdminCon.Refactored

Веб-админка (рефакторинг исходного `CntsAdminCon` с сохранением контракта):

- вход: `POST /account/login` (локальный `Userlist.json` или LDAP + проверка роли в БД), cookie-аутентификация, `GET /account/logout`;
- страницы: `/selectinfo` (информация по документу), `/fasinfo` (ФАС), `/FLmigration` (ФЛ блок, отмена блокировки в PPRS), `/searchb` (поиск СОИД), `/reportinfo` (генератор отчётов — UI поверх API сервиса), `/counter`, `/Error`;
- операции записи: стриминг отмены блокировки в ЦППС (RequestType 106/107, статус CANCEL), отмена ареста в ППТЦ (101/102, ACCEPT), отмена блокировки в PPRS, постановка в очередь, CENTROS-3735;
- журналы `login.log` и `audit.log` в строго определённых форматах;
- работа с 4 БД (PostgreSQL), LDAP (Novell), внешним HTTP API генератора отчётов.

### 1.3. Что тестируем / не тестируем

| В объёме | Вне объёма |
|---|---|
| Функциональное тестирование всех сценариев обоих приложений | Нагрузочное тестирование (отдельная программа) |
| Интеграция админка ↔ API генератора | Тестирование самих БД-источников отчётов |
| Регрессия против исходного `CntsAdminCon` | Penetration-тестирование инфраструктуры |
| Безопасность на уровне приложения (инъекции, ключи, секреты) | Тестирование Quartz/MailKit/ClosedXML как библиотек |
| Эксплуатационные сценарии (ctl.sh, watchdog, ротация логов) | |

## 2. Тестовое окружение

| Компонент | Требование |
|---|---|
| Стенд | Linux x64 (Ubuntu 20.04+), порты 5000 и 5080 свободны, пользователь без root с crontab |
| БД настроек отчётов | PostgreSQL с таблицей `man_reporting_settings` (скрипт `bd.sql`), тестовая схема |
| БД админки | Тестовые копии `cnts_decr_oippg_db`, `cnts_decr_kafka_db`, `abs_gateway_db`, `cnts_exec_pptc_gate_db` |
| БД-источники отчётов | Тестовые PostgreSQL, Oracle, MS SQL с контрольными наборами данных |
| SMTP | Тестовый SMTP (например, MailHog / Papercut) + реальный тестовый SMTP с сертификатом |
| LDAP | Тестовый контроллер домена (LDAPS) |
| Дополнительно | HTTP-заглушка для API генератора (для изолированных тестов админки), исходный `CntsAdminCon` для регрессии |

**Тестовые данные:** минимум 5 отчётов в `man_reporting_settings` (включённый/выключенный, каждый из 3 типов БД, отчёт с битым cron, отчёт с пустым результатом, отчёт с ошибкой SQL); пользователи: локальный из `Userlist.json`, доменный с ролью, доменный без роли, запрещённый пользователь (`DeniedUserName`).

### Критерии входа

- Оба приложения собраны (`dotnet publish -c Release -r linux-x64`) без ошибок и предупреждений.
- Стенд развёрнут по `deploy/DEPLOY.md`, БД и заглушки доступны.
- Тестовые данные загружены.

### Критерии выхода

- 100 % тест-кейсов выполнены; не осталось открытых дефектов критичности Blocker/Critical.
- Все кейсы блоков A–D, H–K пройдены; отклонения задокументированы.
- Регрессия (блок L) не выявила расхождений в контракте, кроме задокументированных в REFACTORING_REPORT.md §6.

### Критичности дефектов

- **Blocker** — потеря/порча данных, утечка секретов, приложение не стартует.
- **Critical** — не работает основной сценарий (прогон отчёта, вход, отмена блокировки, создание отчёта).
- **Major** — неверный статус/текст, обходной путь есть.
- **Minor** — косметика, форматы логов вне контракта.

## 4. Тест-кейсы

Обозначения: **ПУ** — предусловия, **ОР** — ожидаемый результат.

### Блок A. Сервис: шифрование и конфигурация (модульные)

**MRS-01. Protect/Unprotect — круговое шифрование**
- ПУ: задан ключ `k1` (base64, 32 байта), `EncryptionKeyId=k1`.
- Шаги: зашифровать строку подключения через `encrypt`; расшифровать сервисом при старте.
- ОР: значение имеет вид `enc:v1:k1:<base64>`; после расшифровки совпадает с исходным посимвольно (включая спецсимволы `;=@` и кириллицу).

**MRS-02. Два шифрования одного значения дают разный шифротекст**
- Шаги: дважды зашифровать одно значение.
- ОР: шифротексты различны (случайный nonce), оба расшифровываются в исходное значение.

**MRS-03. Расшифровка чужим ключом**
- ПУ: значение зашифровано ключом `k1`; в конфиге только ключ `k2`.
- Шаги: старт сервиса / `encrypt-db`.
- ОР: ошибка `encryption key 'k1' is not configured`; сервис не стартует (проверка ключей при старте), в логе понятное сообщение.

**MRS-04. Подмена keyId в зашифрованном значении**
- Шаги: в строке `enc:v1:k1:...` заменить `k1` на `k2` (ключ `k2` существует); расшифровать.
- ОР: ошибка `cannot decrypt value with key 'k2'` (associated data защищает заголовок); утечки открытого текста нет.

**MRS-05. Повреждённый шифротекст**
- Шаги: изменить 1 символ base64-полезной нагрузки; расшифровать.
- ОР: `SecretProtectionException` с текстом о неверном ключе/повреждении; формат `invalid encrypted value format` при битом base64 или усечении (< 28 байт).

**MRS-06. Невалидные ключи конфигурации**
- Шаги: по очереди задать: ключ не-base64; ключ не 32 байта; `EncryptionKeyId`, отсутствующий в `EncryptionKeys`; `keyId` с недопустимыми символами.
- ОР: старт падает с конкретным сообщением об ошибке для каждого случая.

**MRS-07. Незашифрованные секреты при RequireEncryptedSecrets=true**
- Шаги: оставить `DBConnection` открытым текстом, включить флаг; старт.
- ОР: ошибка конфигурации `value is not encrypted`; при выключенном флаге — старт успешен, значение используется как есть.

**MRS-08. Ротация ключей**
- ПУ: данные зашифрованы `k1`.
- Шаги: добавить `k2`, переключить `EncryptionKeyId=k2`, оставить `k1`; зашифровать новое значение; прочитать старое.
- ОР: старые значения расшифровываются; новые шифруются под `enc:v1:k2:...`.

**MRS-09. Валидация обязательных настроек при старте**
- Шаги: старт без `Settings:DBConnection`; затем с `ConfigPollIntervalSeconds=0`.
- ОР: в первом случае `Settings:DBConnection is required`, во втором — `must be > 0`; процесс завершается, хост не поднимается.

**MRS-10. Приоритет переменных окружения**
- Шаги: задать `Settings__ConfigPollIntervalSeconds=15` при `60` в appsettings.json.
- ОР: опрос конфигурации идёт каждые 15 с (по логам `Start config reading`).

### Блок B. Сервис: HTTP API

ПУ для блока: сервис запущен, `ApiKey` задан; ключ = `K`.

**MRS-11. GET /reports — список статусов**
- Шаги: `curl -H "X-Api-Key: K" http://127.0.0.1:5080/reports`.
- ОР: 200, массив всех отчётов с полями `id, name, cron, enabled, status, runningSince, lastRuntime, nextRuntime, lastState`; статус `Disabled`/`Idle`/`Running` корректен.

**MRS-12. GET /reports/{id}/status — существующий и несуществующий**
- ОР: 200 с DTO для существующего; 404 `{"error":"Report N not found"}` для несуществующего.

**MRS-13. GET /reports/{id} — настройки без секрета**
- ОР: 200; поле `connectionString` в ответе **отсутствует**; есть `connectionStringEncrypted: true/false`; sqlText возвращается.

**MRS-14. Авторизация по X-Api-Key**
- Шаги: запросы без заголовка; с неверным ключом; с верным.
- ОР: 401 (пустое тело) в первых двух случаях; 200 с верным. Сравнение устойчиво к тайминг-атакам (ревью кода: `CryptographicOperations.FixedTimeEquals`).

**MRS-15. /metrics и /health при MetricsRequireApiKey=false/true**
- ОР: при `false` — доступны без ключа; при `true` — 401 без ключа. `/health` возвращает `Healthy`.

**MRS-16. POST /reports/{id}/run — принудительный запуск**
- ОР: 202 `Accepted` с `Location: /reports/{id}/status`, `status=Running`, `startedAt`; после завершения `lastState=Complete`, статус снова `Idle`.

**MRS-17. Повторный run во время выполнения**
- Шаги: запустить «долгий» отчёт, повторить POST run.
- ОР: 409 `Report N is already running` с `runningSince`; второй прогон не стартует.

**MRS-18. Run выключенного отчёта**
- Шаги: POST run для `enabled=false` без и с `?includeDisabled=true`.
- ОР: без параметра — 409 с подсказкой; с параметром — 202 и выполнение; расписание при этом не включается.

**MRS-19. Run несуществующего отчёта** — ОР: 404.

**MRS-20. POST /reports — создание (валидные данные)**
- Шаги: тело `{name, recipients, cron:"0 0 9 ? * MON-FRI", connectionType:"postgresql", connectionString, sqlText, sqlTimeout, errorRecipients}`.
- ОР: 201 `Created`, `Location: /reports/{id}`; в БД строка с `report_last_update=now()`; строка подключения в БД зашифрована (`enc:v1:...`); планировщик подхватил отчёт в течение `ConfigPollIntervalSeconds` (в логе `bTimer istalling`).

**MRS-21. POST /reports — валидация полей**
- Шаги: по очереди: пустое `name`; `name` > 50 символов; `recipients` без `@`; адрес без домена; невалидный cron (`blah`); `connectionType="mysql"`; `recipients` > 4000; `sqlTimeout=-1`; пропуск обязательных полей.
- ОР: 400 `ValidationProblem` с ошибкой по конкретному полю; в БД запись не попадает.

**MRS-22. POST /reports с уже зашифрованной строкой подключения**
- Шаги: передать `connectionString="enc:v1:k1:..."` (корректный) и заведомо нерасшифровываемый `enc:v1:k9:...`.
- ОР: корректный сохраняется как есть; битый — 400 с текстом ошибки расшифровки.

**MRS-23. PATCH /reports/{id} — частичное изменение**
- Шаги: изменить только `cron`; только `enabled=false`; пустое тело (все поля null); PATCH несуществующего id.
- ОР: меняются только переданные поля, `report_last_update` обновляется; пустое тело — 400 `No fields to update`; несуществующий — 404. Выключенный отчёт снимается с таймера при следующем опросе конфигурации.

**MRS-24. Запись запрещена без ApiKey**
- ПУ: сервис запущен без `Settings:ApiKey`.
- ОР: POST/PATCH → 403 `Write operations are disabled...`; GET и run доступны.

**MRS-25. API выключен**
- ПУ: `Settings:ApiEnabled=false`; старт.
- ОР: порт 5080 не слушается; планировщик работает; в логах нет `API starting`.

**MRS-26. API не стартовал (порт занят)**
- ПУ: порт 5080 занят другим процессом.
- ОР: в логе `API failed to start`, планировщик продолжает работать, отчёты выполняются по расписанию.

**MRS-27. Необработанная ошибка в обработчике**
- Шаги: вызвать эндпоинт в момент недоступности БД настроек.
- ОР: 500 `{"error":"..."}`, процесс не падает; последующие запросы обрабатываются.

### Блок C. Сервис: планировщик и выполнение

**MRS-28. Постановка на расписание при старте**
- ПУ: 2 включённых отчёта с валидным cron, 1 выключенный.
- ОР: для каждого включённого — лог `ReportId:N, Name:...` и `bTimer istalling to report id=N on <время>`; выключенный не ставится; `report_next_runtime` корректно.

**MRS-29. Срабатывание по cron — полный прогон**
- ПУ: отчёт на PostgreSQL с cron «каждые 2 минуты», `MailSending=true`, тестовый SMTP.
- ОР: в расчётное время: SQL выполнен, письмо с вложением xlsx отправлено, `report_last_state=Complete`, `report_last_runtime`/`report_next_runtime` обновлены в БД; временный файл удалён.

**MRS-30. Нет параллельных прогонов одного отчёта**
- ПУ: отчёт с SQL `pg_sleep(120)`; cron каждую минуту.
- ОР: пропуски с логом `is already running via API, scheduled run skipped` (или наоборот API↔планировщик); в каждый момент не более одного выполнения.

**MRS-31. Изменение конфигурации во время выполнения**
- Шаги: во время «долгого» прогона изменить cron отчёта в БД.
- ОР: лог `isWork, changed configuration will be applied after the run`; после завершения — `applying postponed configuration`, новый таймер по новому cron; `last_state`/`last_runtime` от завершившегося прогона не потеряны.

**MRS-32. Некорректная строка конфигурации**
- ПУ: строка с битым cron / неизвестным `connection_type` (обходя CHECK — через прямую вставку некорректного JSON в bytea и т.п.).
- ОР: лог `ReportId:N invalid configuration, row skipped: ...`; ошибка записана в `report_last_state`; предыдущая корректная конфигурация продолжает работать; сообщение не дублируется каждый цикл (один раз на `report_last_update`).

**MRS-33. Некорректный cron включённого отчёта**
- ОР: лог `<Setup_bTimer>:` с ошибкой; отчёт не ставится; сервис жив; в админке виден статус ошибки (`Illegal characters for this position`).

**MRS-34. Раннее срабатывание таймера (граница ±1 с)**
- ПУ: быстрый отчёт (выполняется < 1 с) с частым cron.
- ОР: отчёт не уходит дважды на одно срабатывание (защита `EarlyFireTolerance`); в почте по одному письму на срабатывание.

**MRS-35. Инкрементальное чтение конфигурации (watermark)**
- Шаги: подождать 2 цикла опроса без изменений; затем изменить один отчёт.
- ОР: без изменений таймеры не пересоздаются; после изменения перечитан и применён только изменённый отчёт.

**MRS-36. Ошибка БД настроек при опросе**
- Шаги: остановить PostgreSQL на 2 цикла, затем поднять.
- ОР: лог `<ReadConfig>:` с ошибкой, метрика неуспешных чтений растёт, таймеры продолжают работать; после восстановления опрос возобновляется без перезапуска.

**MRS-37. Graceful shutdown**
- Шаги: во время прогона выполнить `ctl.sh stop`.
- ОР: лог `Waiting for N running report(s) to finish`; завершение в пределах таймаута (~30 с), затем SIGKILL при превышении; после рестарта состояние в БД консистентно.

**MRS-38. Таймаут SQL**
- ПУ: отчёт с `sql_timeout=5` и запросом `pg_sleep(30)`.
- ОР: прогон прерывается ~через 5 с, `last_state` содержит текст ошибки таймаута; письмо об ошибке уходит на `report_error_recipinet`.

**MRS-39. Неподдерживаемый тип подключения в ручном запуске**
- Шаги: отчёт с `connection_type` вне списка (если удастся вставить) → POST run.
- ОР: после прогона `last_state = "Query failed or unsupported connection type '...'"`.

### Блок D. Сервис: цепочка SQL → Excel → почта

**MRS-40. Экспорт xlsx — структура**
- ПУ: отчёт, возвращающий 1+ таблиц с типами: int, numeric, text (кириллица), timestamp, NULL.
- ОР: файл открывается в Excel/LibreOffice; листы по таблицам; типы и NULL корректны; кириллица без «кракозябр»; автоширина колонок применена.

**MRS-41. Большой результат**
- ПУ: запрос на ~100 тыс. строк.
- ОР: файл создаётся и отправляется; нет OOM; метрика строк зафиксирована; файл удалён после отправки.

**MRS-42. Пустой результат запроса**
- ОР: прогон завершается штатно (письмо с пустым отчётом или зафиксированное поведение), `last_state` соответствует; падения нет.

**MRS-43. Имя файла**
- ОР: формат `Rep_{id}_{ГГГГ-ММ-ДД_ЧЧ-ММ-СС}.xlsx`; при запуске через API — суффикс `_api`.

**MRS-44. Отправка почты — получатели**
- ПУ: `recipients="a@t.ru; b@t.ru;;  "` (двойной `;`, пробелы, хвостовой разделитель).
- ОР: письмо уходит ровно двум адресатам; пустые элементы пропущены; тема `Отчет: {name} (id:{id}) от {дата}`.

**MRS-45. Ошибка SMTP**
- ПУ: недоступный SMTP-сервер.
- ОР: `Send` возвращает false → `last_state` начинается с `Sending mail report error`; ошибка в логе `<MsgSendkit>`; xlsx удалён; отчёт останется в расписании.

**MRS-46. Ошибка выполнения отчёта → письмо об ошибке**
- ПУ: отчёт с синтаксически неверным SQL.
- ОР: письмо на `errorRecipients` с телом = тексту ошибки; `last_state` содержит `Message + StackTrace`; обычные получатели письмо не получают.

**MRS-47. MailSending=false**

### Блок M. Безопасность

**SEC-01. SQL-инъекция в фильтре Kafka**
- Шаги: фильтр `' OR '1'='1`; `'; DROP TABLE ...--`.
- ОР: фильтр трактуется как текст (параметр `@Filter`); данных не возвращается/нет ошибки SQL; таблицы целы.

**SEC-02. LDAP-инъекция**
- Шаги: логин `*)(uid=*`, `admin)(|(password=*)` и т.п.
- ОР: экранирование по RFC 4515; вход не выполняется; ошибки LDAP нет.

**SEC-03. Секреты в ответах API и логах**
- ОР: `connectionString` не возвращается ни одним эндпоинтом; в логах нет строк подключения, паролей SMTP, ключа API и ключей шифрования (поиск по логам после полного прогона всех сценариев).

**SEC-04. Файлы с секретами на стенде**
- ОР: `app.env` и `appsettings.json` генератора — права 600, каталоги 750; `Userlist.json` и `appsettings.Development.json` отсутствуют в прод-поставке админки.

**SEC-05. Антифорджери и cookie**
- ОР: POST `/account/login` без антифорджери-токена отклоняется; cookie `HttpOnly`, `SameSite` по умолчанию; сессия после logout невалидна.

**SEC-06. Доступ к API генератора с чужого хоста**
- ПУ: `ApiUrl=http://127.0.0.1:5080`.
- ОР: с внешней машины порт недоступен; при `0.0.0.0` — доступ только с ключом, чтение и запуск без ключа — 401.

**SEC-07. Произвольный SQL через создание отчёта**
- ОР: возможен только с валидным `X-Api-Key`; без ключа — 401/403 (зафиксировать как документированный риск: страница доступна любому вошедшему пользователю админки — рекомендация ограничить ролью).

## 6. Риски и рекомендации

1. **Страница «Генератор отчетов» доступна любому вошедшему пользователю**, а ключ API позволяет выполнять произвольный SQL — рекомендуется ограничить доступ ролью (сейчас роль одна — `User`).
2. **SMTP-сертификат не проверяется** (`ServerCertificateValidationCallback = true`) — унаследовано; зафиксировать как принятый риск или закрыть отдельной задачей.
3. **API генератора по HTTP без TLS** — допустимо только при `127.0.0.1`; контролировать при изменении `ApiUrl` (SEC-06).
4. **Пароли в `Userlist.json` открытым текстом** — ограничить права файла (600), планировать замену на хэши.
