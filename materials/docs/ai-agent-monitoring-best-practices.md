## 1. Уровни автономии: начинать с co-pilot, не с автопилота

Индустрия выделяет уровни автономии агента (ilert, Agentic Incident Management Guide):

| Уровень | Режим | Что делает агент | Риск |
|---|---|---|---|
| **L1** | Co-pilot | Собирает факты, анализирует, советует. Действия read-only | Минимальный |
| **L2** | Supervised | Предлагает действие, выполняет после подтверждения человека | Средний |
| **L3** | Autonomous | Сам перезапускает сервисы, откатывает деплой по runbook | Высокий, требует зрелости |

**Практики:**
- Стартовать с L1: агент только наблюдает и советует, доверие накапливается 2–4 недели «теневого» режима, рекомендации логируются без исполнения.
- Переход на L2 — через явное подтверждение (кнопка/команда в мессенджере), каждое действие — в аудит-лог.
- L3 — только для детерминированных действий с откатом (перезапуск службы), никогда для деструктивных операций.

**У нас:** агент сейчас чистый L1 (мониторинг, анализ, отчёты; перезапуск приложений делает только тупой watchdog crontab без LLM). Логичный следующий шаг — L2: команда `/restart man_reporting` с подтверждением.

## 2. Телеметрия: четыре золотых сигнала + три столпа

**Сигналы (что мерить):**
- Четыре золотых сигнала Google SRE: **latency, traffic, errors, saturation** — минимальный набор для каждого сервиса.
- RED-метод для сервисов (Rate, Errors, Duration) и USE-метод для ресурсов (Utilization, Saturation, Errors).
- Три столпа наблюдаемости: **метрики, логи, трейсы**. Метрики дешёвые и показывают «что», логи — «почему», трейсы — «где» в распределённой системе.
- Стандарты: Prometheus-формат `/metrics`, OpenTelemetry для трейсов и унифицированной телеметрии — не изобретать свои схемы (groundcover рекомендует OTel GenAI semantic conventions даже для самих AI-агентов).

**Практики:**
- Снимки метрик с фиксированным интервалом и историей ≥ 24–48 ч для расчёта динамики (min/avg/max, дельты).
- Health-check на двух уровнях: синтетический HTTP-пробник (`/health`) + наличие процесса — ловит разные классы отказов.
- Мониторить зависимости отдельно (БД, внешние API): отказ PostgreSQL иначе маскируется под отказ приложения.

**У нас:** ✅ снимки каждые 5 мин с 2-суточной историей, health на двух уровнях, отдельная проверка `pg_isready`, метрики приложения из `/metrics` (Prometheus-формат). 🔲 Нет: latency/ttraffic приложений (время ответа `/health`, RPS), трейсинг (для двух сервисов избыточен, но OTel-метрики CntsAdminCon стоит добавить).

## 3. Алертинг: борьба с шумом — главная задача

Alert fatigue — причина №1 провала мониторинга: SRE-команды получают тысячи алертов в день, пороговые схемы дают лишь 45–65% точности RCA (Mendeley, Intelligent SRE).

**Практики:**
- **Дедупликация по сигнатуре**: нормализовать ошибку (убрать числа, id, timestamps) и не алертить повторно в окне 30–60 мин.
- **Группировка (корреляция)**: несколько симптомов одного инцидента — одно сообщение («сервис недоступен + процесс упал + health 503» = один инцидент, а не три алерта).
- **Severity-уровни**: критичное (сервис недоступен) — немедленно; предупреждения (диск 85%) — с троттлингом; информационное — только в дайджест.
- **Flapping-защита**: алерт на восстановление только после N минут стабильной работы.
- Время простоя считать и сообщать явно («простой 89 с»).

**У нас:** ✅ дедупликация по сигнатуре (30 мин), троттлинг диск-алерта (6 ч), отдельные 🔴/🟠/⚠️ уровни, длительность простоя в 🟢. 🔲 Нет: корреляции симптомов в один инцидент (сейчас «health недоступен» и «процесс не найден» приходят двумя сообщениями), flapping-защиты.

## 4. LLM в контуре мониторинга: grounding и защита от галлюцинаций

Splunk и обзоры arXiv сходятся в правилах работы LLM с операционными данными:

**Практики:**
- **Grounding**: LLM получает только факты (JSON с метриками, фрагмент лога), а не «память» — и отвечает строго по ним. Системный промпт фиксирует роль, стиль и объём («дежурный SRE-аналитик, до 6 предложений, без воды»).
- **Чанкинг**: большие логи резать на блоки, в LLM отправлять только релевантный фрагмент ошибки (первые N строк + stack trace), иначе стоимость и таймауты.
- **Детерминизм**: низкая температура (0–0.2) для аналитических задач.
- **Валидация выхода**: для машинно-читаемых результатов требовать строгий JSON-schema; для текстовых — человек в контуре (LLM может неверно атрибутировать причину).
- **Graceful degradation**: LLM недоступен → отправляется шаблонный отчёт без анализа, мониторинг не ломается.
- **Разделение ролей**: детекция — детерминированная (пороги, правила), LLM — только интерпретация и рекомендации. Никогда не отдавать LLM решение «алертить или нет».
- Для сложных систем — мультиагентная схема: отдельные агенты для логов / метрик / трейсов / инфраструктуры под координатором (Mendeley: точность RCA растёт против одного LLM).

**У нас:** ✅ grounding через JSON фактов, системный промпт SRE, temperature 0.2, чанкинг логов (первые 600 символов), fallback-отчёт без LLM, детекция детерминированная. 🔲 Нет: валидации ответов LLM (модель периодически игнорирует «без markdown» — стоит добавить пост-обработку), схемы для `/ask`.

## 5. RCA: от симптомов к причине

**Практики (по ai-incident-analysis-agent, DiogoRibeiro7):**
- Слоистый пайплайн: ingestion → нормализация (единый timeline, UTC) → детекция аномалий (правила + скользящий baseline) → корреляция во времени и по графу зависимостей → ранжирование evidence → LLM-резюме.
- LLM получает **EvidenceBundle** — структурированный набор фактов инцидента, а не сырой поток; ответ привязан к цитируемым фактам.
- RAG по истории инцидентов и runbook: «похожий инцидент 12.03, решение — …» резко повышает качество рекомендаций.
- Blameless post-mortem по каждому значимому инциденту: timeline, root cause, remediation, уроки — и пополнение базы знаний агента.

**У нас:** ✅ LLM-анализ по факту инцидента. 🔲 Нет: baseline-аномалий (алерт при аномальном росте RSS/CPU, а не только при отказе), истории инцидентов как базы знаний (incidents есть в state.json — можно подавать похожие прошлые инциденты в промпт), post-mortem.

## 6. Отчётность и SLO

**Практики:**
- Ежедневный дайджест в фиксированное время: статус, инциденты, ошибки, ресурсы, рекомендации — LLM-резюме поверх структурированных фактов.
- Дашборды и отчёты строить вокруг **результата** (сервис делает свою работу?), а не только «процесс жив»: для man_reporting это успешные прогоны отчётов.
- Метрики самого мониторинга: **MTTD** (время обнаружения), **MTTR** (время восстановления), доля ложных алертов, доля инцидентов без алерта — качество агента измеряется, а не ощущается.
- Долговременное хранение отчётов (архив по дням) для ретроспектив и трендов.

**У нас:** ✅ дайджест 09:00 МСК с LLM-сводкой, графиками и HTML-отчётом, длительности простоев фиксируются (база для MTTD/MTTR). 🔲 Нет: явного расчёта MTTD/MTTR за период, SLO (например «доступность 99%»), архива отчётов.

## 7. Безопасность агента

**Практики:**
- Read-only по умолчанию: агент не должен иметь технической возможности сломать прод (Splunk/ilert: L1 = read-only).
- Секреты (токены бота, LLM-ключи) — в файле с правами 600, никогда в логах и в промптах; маскировать PII/секреты в отправляемых LLM фрагментах логов.
- Бот обслуживает только зарегистрированный chat_id, чужие чаты — отказ.
- Аудит: каждое действие и отправленное сообщение — в лог с меткой времени.
- Минимальные права ОС: агенту не нужен root; sudo только для точечных команд (psql).

**У нас:** ✅ app.env с правами 600, привязка к chat_id, логирование отправок. 🔲 Нет: маскирования секретов в логах перед отправкой в LLM (пароли БД в строках подключения могут попасть в промпт), агент работает от root.

## 8. Надёжность самого агента («кто сторожит сторожа»)

**Практики:**
- Внешний watchdog (systemd/cron), перезапуск при падении; агент не должен умирать молча.
- Self-monitoring: heartbeat — если от агента нет признаков жизни N минут, внешняя проверка шлёт алерт.
- Деградация без потери данных: state сохраняется атомарно (tmp + rename), переживает перезапуск.
- Сетевые ошибки (Telegram, LLM API) — ретраи с backoff, очередь не теряется.
- Агент — stateless-логика + единственный state-файл: код можно обновлять без потери истории.

**У нас:** ✅ crontab-watchdog, атомарный state.json, ретраи отправок. 🔲 Нет: heartbeat-алерта, если мёртв и агент, и watchdog (нужна проверка снаружи, хотя бы «агент молчит 30 мин» от крон-скрипта с прямой отправкой в TG).

## 9. Внедрение: дорожная карта

По ilert и Middleware — порядок внедрения:

1. **Неделя 1–2**: read-only агент, узкий скоуп (1–2 сервиса), базовые сигналы, Telegram-алерты. *(У нас — сделано.)*
2. **Неделя 3–4**: LLM-анализ инцидентов, дайджесты, обучение команды, сбор обратной связи о точности. *(У нас — сделано.)*
3. **Месяц 2**: baseline-аномалии, корреляция симптомов, RAG по истории инцидентов, MTTD/MTTR-метрики, архив отчётов.
4. **Месяц 3+**: L2-действия с подтверждением (перезапуск, очистка диска), runbook-автоматизация, расширение на остальные сервисы.
